## 背景与问题

三条词法路径对中文都没有有效的分词，查询组合又要求全部词同时出现：

- FTS5 的 `unicode61` tokenizer 把两个空白之间的整段汉字当成一个词项。
  "我想知道北京的天气怎么样"是一个词项，查"北京"零命中。
- 进程内词法腿与 `TokenOverlapContextReranker` 只收集 `[a-z0-9_]` 连续段，
  纯中文文本产出零个词元。
- `storage::fts_match_expression` 把查询按空白切成短语后用 AND 连接。自然语言
  问句（"calibration 文件在哪"）因此必然落空，英文问句同样如此。

交付代码在[混合检索基准](../benchmarks/memory-hybrid-retrieval-v1.md)的 20 条查询上，
纯词法配置只答出 2 条（`QL6`、`QL7`，靠空格分隔的英文标识符），记录为 R@*=0.100。
当时的结论"语义腿是决定性增量"有一部分是词法腿没有工作造成的。

现有 FTS 相关测试没有一条使用中文，所以缺陷一直未被触发。会话分段还按字节截断
超长消息：中文被截在字符中间时产生非法 UTF-8，整个会话的索引重建以 `DataLoss`
失败（`BUG-20261124-001`）。

实施中又确认了两处被 AND 语义掩盖的既有缺陷。查询改为 OR 之后它们会成为主要
行为，所以一并修复：

- **词法腿按相关度倒序返回**（`BUG-20261124-002`）。`SqliteMemoryStore` 把 bm25 的
  大小归一化成 `1 / (1 + |rank|)`，匹配越强值越小，而两种融合模式都按值越大越靠前，
  于是多命中时从弱到强返回。实测：bm25 为 -2.17、-1.62、-1.19 的三条记录，交付代码
  按 -1.19、-1.62、-2.17 返回。此前没有暴露，是因为 AND 下几乎没有多命中；命中词
  太常见时 bm25 又全部并列，靠并列规则碰巧顺序正确。
- **`exact_terms` 在没有记录命中时被跳过**（`BUG-20261124-003`）。过滤条件取决于
  是否有记录包含该词。失败签名检索（DEC-029）同时设置 `exact_terms` 与文本查询，
  一个还没有历史记录的工作流因此会拿回其他工作流里与原因码共用一个词的记录。会话
  索引与进程内索引原本就是强制的。

## 决策

会话索引的发言投影、查询单元与命中证据后来由
[DEC-171](DEC-171-conversation-speech-search.md) 修订。

### 1. 单一的确定性分词契约

新增公开头 `include/mira/text_segmentation.hpp`，纯 Core，无词典、无平台依赖、
无外部头族：

- 先归一化：全角 ASCII（U+FF01–U+FF5E）转半角，零宽字符与变体选择符删除，ASCII
  字母折叠为小写，非法 UTF-8 字节按分隔符处理。
- 以空格分词的文字每个字母数字连续段是一个 `Word`，与 `unicode61` 的词项一致。
- 汉字和假名每个字是一个 `Character`，相邻两个字是一个 `Bigram`。
- 消费方按用途选单元集合：`IndexUnits`（词 + 字）供耐久 FTS5 索引存储；
  `MatchUnits`（词 + 字 + bigram）供查询匹配；`CoarseUnits`（词 + bigram，单个字
  自成一段时取该字）供集合与多重集合重叠类消费方使用。
- 同一头文件提供按码点边界截断的 `truncate_utf8`，取代各处按字节 `resize` 的写法。

### 2. 索引侧只存字，bigram 放在查询侧

耐久 FTS5 表继续使用 `unicode61`，写入时绑定 `IndexUnits` 拼接的索引文本。查询时
`Bigram` 写成两个字的短语（`"蓝 牙"`），FTS5 按词元位置匹配，等价于 bigram 匹配。
不注册自定义 tokenizer，不引入词典、可加载扩展或 ICU。

### 3. 查询组合改为 OR，由 bm25 排序，规模有界

- `fts_match_expression` 把查询的 `MatchUnits` 逐个加引号后用 OR 连接，按首次出现
  去重。每个单元仍加引号，用户文本不能注入 FTS5 运算符的性质不变。
- 一个查询最多匹配 128 个去重后的单元。超出的部分按"词、bigram、字"的次序放弃，
  每组内部等步长保留以覆盖整段文本；store 置 `quality.degraded`，并在 `note` 中
  说明只匹配了一个子集。
- 词法贡献是 `m / (1 + m)`，其中 `m` 是 bm25 分数的绝对值：索引不给权重的匹配为 0，
  越强越接近 1。两种融合模式都按值越大越靠前，与 bm25 的方向一致。
- `exact_terms` 是唯一的"必须命中"通道。只要查询声明了它，`SqliteMemoryStore` 就
  只返回逐字包含全部词的记录，无论是否有记录满足。需要全词命中的调用方使用它。

### 4. 各消费方的落点

- `SqliteMemoryStore`：`memory_fts` 表结构不变，行内写入索引文本。
  schema 1.8 → 1.9，打开时按已索引的记录重建全部 FTS 行。
- `SqliteConversationIndex`：片段表和外部内容 FTS5 表都用 `lexical` 表示索引文本，
  插入和删除触发器同步该列，FTS5 可用同一列执行完整性校验与重建。
  schema 1.0 → 1.1，打开时丢弃旧索引并原地重建，水位、摘要和擦除屏障保持有效，
  历史会话无需宿主重建即可继续检索。有文本条件时按 bm25 升序（越相关越靠前）
  返回，同分按来源序号倒序和 ID，`lexical_score` 携带第 3 节的贡献值；没有文本
  条件时排序不变。
- `InMemoryContextIndex` 词法腿与 `TokenOverlapContextReranker` 使用 `CoarseUnits`。
  这两处没有逆文档频率来压制常见字，单字会产生十倍以上的部分匹配。

### 5. 不在本决策内

- 词典分词（jieba 等）。本契约的索引侧不依赖词典，日后若引入只需在查询侧把词
  转成词级短语，不需要重建索引。
- LLM token 计数（`bytes/3`、`bytes_per_token`）。它与词法分词是两个问题。
- 身份键归一化。claim key 与社交 alias key 是持久化身份，保持不变。
- 内容标记扫描前的归一化、繁简与拼音、英文词干还原。
- `WeightedSum` 融合模式的权重。该模式把先验线性叠加，多命中时先验可以盖过词法
  差异，这是它一直以来的性质，也是 DEC-113 把默认翻成 `ReciprocalRank` 的理由。

## 备选方案

| 方案 | 结论 | 依据（纯词法腿 R@10，语料 44 / 4,044 / 40,120 篇） |
| --- | --- | --- |
| 只换分词，保留 AND | 否决 | 0.150 / 未测 / 未测，任何分词都一样 |
| 只换组合，保留 `unicode61` 原文 | 否决 | 0.350 / 0.350 / 0.350 |
| SQLite 内置 `trigram` | 否决 | 0.350 / 0.350 / 0.300；少于 3 个字符不匹配 |
| 单字，OR | 可用 | 0.950 / 0.800 / 0.567 |
| bigram 索引，OR | 可用 | 0.833 / 0.683 / 0.642 |
| jieba 分词，OR | 暂不引入 | 0.808 / 0.758 / 0.642；需 8.2 MB 词典、约 64 MB 常驻 |
| 单字 + bigram 双份索引 | 否决 | 与所选方案逐项相同，索引体积 1.7 倍 |
| **单字索引 + 查询侧 bigram 短语，OR** | **采用** | **0.950 / 0.783 / 0.592** |
| 先 AND，结果不足再回退 OR | 否决 | 20 条查询全部回退，只多一次查询 |
| 不设单元数上限 | 否决 | 最大的合法查询在 4 万篇索引上约 1 秒，期间占住 store 的工作线程 |
| 超出上限时拒绝查询 | 否决 | 宿主按设计会把多段文本拼进查询，拒绝会把原本返回空的调用变成错误 |
| 自定义 FTS5 tokenizer 或可加载扩展 | 否决 | 查询组合仍需应用侧分词；SQLite 以 `SQLITE_OMIT_LOAD_EXTENSION` 编译；引入平台依赖 |
| 会话索引迁移时清空、由宿主重建 | 否决 | 升级后历史会话在重建前不可检索 |

测量条件见[词法分词维护计划](../plans/maintenance-2026-11-lexical-segmentation.md)。
语料是基准数据集的 44 条记忆加上从 `docs/` 抽取的中文段落，只有 20 条查询，
各真实分词方案之间约 10 个百分点以内的差异不具有分辨力。

## 影响与风险

- **契约变更**：多词查询从"全部出现"变为"任一出现，按相关度排序"，结果集变大。
  依赖旧语义的调用方应改用 `exact_terms`；`exact_terms` 现在在所有后端都是强制的。
- **排序变更**：会话索引有文本条件时不再按时间返回；`SqliteMemoryStore` 的词法腿
  从弱到强的倒序改为由强到弱。
- **DEC-113 的锚点**：无查询向量时，默认融合保持词法腿的顺序；它与 `WeightedSum`
  同序只在词法差距大于先验差距时成立，不再是普遍保证。
- **持久化格式**：两个 store 各升一个小版本。索引文本是原文的派生副本，受相同的
  擦除与 `secure-delete` 约束。索引体积增加，4 万篇中文段落上比原文索引多约 29%。
- **性能**：OR 需要给全部命中排序。本机内存库 4 万篇上最慢的查询约 26 毫秒
  （`LIMIT 512`）；移动端未测。
- **口径差异**：非 ASCII 字母的大小写折叠与变音符号去除只在 FTS5 腿由 `unicode61`
  进行，进程内腿按原样比较。三处 exact 腿的大小写口径也不一致
  （`SqliteMemoryStore` 区分大小写，其余不区分），本记录未改动。
- **未覆盖的文字**：泰语等不用空格分词的非 CJK 文字仍是整段一个词项。
- **基准失效**：DEC-112 与 DEC-113 引用的纯词法基线和各配置差值在修复词法腿后
  不再成立，重测完成前不得继续引用。

## 验证方式

- 契约测试冻结分词与 UTF-8 截断的公共语义。
- store 测试覆盖中文召回、相邻双字优先于分隔或倒序命中、两个 schema 迁移、
  新建和迁移后的会话 FTS5 外部内容完整性，以及超长中文消息的索引重建。
- 进程内词法腿与重排器的中文用例。
- 以基准数据集驱动交付 `SqliteMemoryStore` 的词法腿质量门（R@10 下限 0.90）。
- 全量 `ctest` 与 architecture、platform-boundary、docs、sbom、format 五项门禁。
