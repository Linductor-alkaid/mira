# Mira 项目管理与文档规范

> 状态：Active  
> 版本：1.0  
> 生效日期：2026-08-29  
> 适用范围：Mira 的代码、测试、设计、计划、决策、验证记录和发布材料

## 1. 目的

本文定义 Mira 的项目规划、任务跟踪、技术决策、文档编写、验证取证和变更同步规则。
目标是让每项工作都能回答以下问题：为什么做、由什么设计约束、当前做到哪里、如何证明
完成，以及后续如何复现结论。

本文借鉴 Heyaki 的里程碑拆分、稳定任务编号、退出条件和验证记录方法，但内容以 Mira 的
Agent Runtime、跨平台边界和 Executor 强制约束为准，不继承其他项目的产品范围、发布渠道
或仓库权限规则。

## 2. 规范效力与文档关系

仓库内规则按以下顺序解释：

1. 用户或维护者对当前工作的明确要求。
2. 根目录 `AGENTS.md` 中的仓库级强制约束。
3. 本文中的项目管理与文档规范。
4. 已批准的设计文档和决策记录。
5. 总计划、里程碑计划和工作项中的局部约定。

低层文档不得静默覆盖高层约束。若实现需要改变已生效的架构、公开契约、安全边界、
Executor 使用方式或产品默认值，必须先新增或更新决策记录，再同步修改设计、计划和测试。

文档承担不同职责，不互相替代：

- 设计文档说明系统应如何工作以及为什么这样设计。
- 决策记录说明一个有实质影响的选择、备选方案和后果。
- 计划文档说明交付顺序、范围、状态、依赖和验收方式。
- 测试及验证记录说明某项声明在什么条件下得到证明。
- 代码和配置是实际行为的实现，但不能作为缺失契约文档的长期替代品。

## 3. 文档目录

文档按用途放置；目录在出现首份对应文档时创建：

| 路径 | 内容 | 典型文件 |
| --- | --- | --- |
| `docs/design/` | 架构、模块、协议、状态机和跨层契约 | `mira_runtime_design.md` |
| `docs/decisions/` | 架构决策和产品默认值记录 | `DEC-001-runtime-executor-ownership.md` |
| `docs/plans/` | 总计划、里程碑计划和交付清单 | `mira-implementation-plan.md`, `m1-core-contracts.md` |
| `docs/security/` | 威胁模型、安全策略、隐私和凭据处理 | `threat_model_and_confirmation.md` |
| `docs/compatibility/` | 平台、编译器、依赖和 Provider 兼容性证据 | `android-ndk-matrix.md` |
| `docs/supply-chain/` | 依赖锁定、许可证、SBOM 和升级审计 | `dependency-policy.md` |
| `docs/benchmarks/` | 性能目标、方法、原始条件和结果摘要 | `controller-latency.md` |
| `docs/executor_feedback/` | Executor 能力缺口反馈台账 | `ledger.md` |
| `docs/project/` | 本规范及其他仓库级协作流程 | 本文 |

不要用一个“总文档”承载所有内容。安全结论、兼容性声明、性能数据和供应链证据应保留在
各自目录，由设计或计划通过相对链接引用。

## 4. 项目规划层级

### 4.1 总计划

总计划是项目交付范围与进度的唯一入口，建议使用
`docs/plans/mira-implementation-plan.md`。它至少包含：

- 当前整体状态和最近更新时间。
- 交付边界、明确非目标和不可破坏的架构约束。
- 里程碑索引、依赖关系和建议发布点。
- 尚未冻结的产品或技术决策及其链接。
- 跨里程碑通用质量门禁。

总计划保持概览性质。具体任务、测试和逐轮实施证据放到独立里程碑文档，避免总计划因
流水记录而失去可读性。

### 4.2 里程碑计划

每个里程碑使用独立文件，例如 `docs/plans/m1-core-contracts.md`，并必须声明：

- 状态、负责人、所属总计划和最后更新时间。
- 目标、范围、非目标、前置依赖和建议发布点。
- 带稳定编号的工作项。
- 测试矩阵和退出条件。
- 风险、阻塞项及相关设计或决策链接。
- 按日期追加的实施与验收记录。

里程碑应产生一个可独立验收的能力增量。仅以代码目录、人员分工或时间周期划分，且没有
可观察交付结果的内容，不适合作为里程碑。

### 4.3 工作项

工作项是可验收的最小计划单位，使用 `M<里程碑>-<两位序号>`，例如 `M1-03`。一项工作
应描述结果而非活动：使用“提供可取消的 Task 状态推进并覆盖终态幂等测试”，而不是
“研究状态机”。

工作项必须能关联到至少一项验收方式。预计需要跨多个模块、无法由单次评审验证或包含多个
独立结果时，应拆分为多个工作项。

缺陷、风险和临时兼容措施可使用以下编号：

- `BUG-YYYYMMDD-NNN`：需要跨提交跟踪的重要缺陷。
- `RISK-YYYY-NNN`：影响里程碑或发布的已识别风险。
- `DEC-NNN`：架构或产品决策。
- `EXE-YYYYMMDD-NNN`：仅用于既有 Executor 反馈台账。

编号一经被引用不得复用；项目扩大到编号冲突时可增加领域前缀，但同一文档内必须一致。

## 5. 状态与勾选规则

计划、里程碑和工作项使用以下状态词，不自造含义相近的状态：

| 状态 | 含义 |
| --- | --- |
| `Proposed` | 已提出，范围或方案尚待评审 |
| `Planned` | 范围、依赖和验收方式已明确，可排期 |
| `In Progress` | 已开始实施，尚未满足完成定义 |
| `Blocked` | 有明确外部阻塞，已记录负责人和解除条件 |
| `Completed` | 实现和全部适用退出条件已通过 |
| `Superseded` | 已由另一文档或决策替代，保留历史链接 |
| `Cancelled` | 明确终止且不再计划交付，保留原因 |

决策记录使用 `Proposed`、`Accepted`、`Superseded` 或 `Rejected`：`Accepted` 表示已批准并
生效，`Rejected` 表示经评审未采用。决策状态不用于表示实施进度；其落地进度由关联的计划
工作项跟踪。

清单勾选必须遵守以下规则：

1. 只有实现、测试、必要文档和本项验收均完成后，才能从 `[ ]` 改为 `[x]`。
2. “代码已写完”“本机能编译”或“提交已合并”本身不等于完成。
3. 因设备、权限、网络、凭据或平台缺失而未执行的验证必须保持 `[ ]`，不得用 skip、预期
   通过或其他平台的结果冒充成功。
4. 未执行项必须记录原因、所需环境、负责人和可操作的补跑条件。
5. 工作项全部完成不自动关闭里程碑；所有退出条件也必须逐项通过并留下验证记录。
6. 重新打开已完成工作时保留原验证记录，说明失效原因，并将状态或复选框恢复为未完成。

## 6. 准入与完成定义

### 6.1 Definition of Ready

非平凡工作进入 `In Progress` 前至少满足：

- 目标、范围和非目标可被复述且没有关键歧义。
- 所属里程碑或维护任务明确，并已有稳定编号。
- 相关设计、决策和公开契约已定位；需要改变它们时已有同步更新安排。
- 依赖、风险、平台条件和 Executor 承载方式已识别。
- 验收标准可执行，所需测试环境已知。
- 涉及用户数据、凭据、外部副作用或 Human Takeover 时，安全与恢复行为已定义。

小型拼写修复、无行为变化的格式调整等可不创建独立计划项，但仍必须遵守相关文档规则。

### 6.2 Definition of Done

一项变更只有同时满足以下条件才可完成：

- 实现符合分层、所有权、取消、错误和 Executor 生命周期约束。
- 新增或变更行为具有与风险相称的自动化测试。
- 适用的构建、测试、静态检查、平台验证或基准已经执行并通过。
- 公开 API、配置、事件 schema、错误语义和示例已同步更新。
- 受影响的设计、决策、计划、安全、兼容性和供应链文档已同步更新。
- 验证记录包含可复现证据；未验证声明被明确限定。
- 不存在被吞掉的失败、无主异步任务、未闭合取消路径或未登记的 Executor 能力绕行。

## 7. 里程碑文档模板

新建里程碑文件时使用以下基本结构，可按领域增加小节，但不能删除状态、任务、退出条件和
验证记录：

```md
# M1：里程碑名称

> 状态：Planned
> 负责人：姓名或团队
> 所属计划：Mira 实施总计划（创建文件时改为实际相对链接）
> 前置：M0
> 建议发布点：Runtime alpha
> 更新日期：YYYY-MM-DD

## 目标

## 范围与非目标

## 设计与决策依据

## 工作项

- [ ] `M1-01` 以可验收结果描述任务。

## 风险与阻塞

## 测试与退出条件

- [ ] 给出可观察、可执行的通过条件。

## 验证记录

YYYY-MM-DD：记录 commit、环境、命令、结果、限制和剩余项。
```

验证记录按时间追加。可以修正事实错误，但不得重写历史使失败、回退或环境限制消失。

## 8. 决策记录

以下变化必须建立或更新 `docs/decisions/` 中的记录：

- 跨模块依赖方向、所有权和生命周期。
- 公开 API、持久化格式、事件 schema 或兼容性承诺。
- 模型、工具、记忆、动作和平台 Provider 的核心契约。
- 安全边界、默认权限、数据保留和敏感信息处理。
- 关键依赖、支持平台、性能目标或产品默认值。
- 明显改变实现复杂度、迁移成本或未来扩展方向的取舍。

决策使用 `DEC-NNN` 稳定编号。尚待确认但为推进验证而采用的选择必须标为“暂定默认值”，
同时填写负责人和最迟冻结里程碑，不能把暂定值写成既定事实。

```md
# DEC-001：决策标题

> 状态：Proposed | Accepted | Superseded | Rejected
> 日期：YYYY-MM-DD
> 负责人：姓名或团队
> 冻结里程碑：M1
> 替代/被替代：无

## 背景与问题

## 决策

## 备选方案

## 影响与风险

## 验证方式

## 关联文档和工作项
```

推翻既有决策时，新记录应链接旧记录，旧记录改为 `Superseded` 并反向链接新记录。禁止删除
已被代码、计划或发布说明引用的历史决策。

## 9. 设计文档规范

设计文档至少包含：

- 元数据：状态、版本、更新日期、负责人或适用范围。
- 背景、目标和非目标。
- 系统上下文、模块职责与依赖方向。
- 数据模型、接口、状态机、时序或控制流。
- 所有权、并发、Executor 路由、取消、超时和 shutdown 语义。
- 错误处理、恢复、幂等、背压及资源上限。
- 安全、隐私、可观测性、Replay 和兼容性考虑。
- 备选方案、已知限制、分阶段落地方案和测试策略。
- 关联决策、计划、反馈台账和后续问题。

文档中的“必须”“不得”表示强制约束；“应该”表示有充分理由才可偏离；“可以”表示可选。
使用绝对性能、实时性、跨平台、安全或兼容性措辞时，必须链接相应证据。代码片段应标明其
是规范接口、伪代码还是草案，避免读者误认为已经实现。

图用于表达难以从文字直接看清的依赖、状态或时序。图中的名称必须与正文和代码术语一致，
图不能替代错误路径、边界条件和所有权说明。

## 10. 验证证据

每条重要验收记录应包含：

- 日期和对应 commit 或工作树状态。
- 操作系统、架构、设备或模拟器、编译器和关键依赖版本。
- 构建类型、feature flags、模型/Provider 配置等影响结果的条件。
- 可复现的准确命令或 CI job/run 链接。
- 通过、失败或未运行的结果，以及关键计数或指标。
- 已知限制、失败归属、负责人和补跑条件。

以下声明必须区分证据等级：

| 声明 | 最低证据 |
| --- | --- |
| 源码或配置支持 | 对应代码、配置和静态检查 |
| 可以编译 | 指定工具链和配置的实际构建结果 |
| 可以运行 | 目标环境中的运行或集成测试 |
| 可互操作 | 与明确版本对端的端到端验证 |
| 满足性能目标 | 固定方法、样本、硬件和统计结果 |
| 满足实时性目标 | 延迟分布、调度条件、过载和取消边界实测 |
| 跨平台支持 | 每个被声明平台的构建和适用运行门禁 |

测试 skip 是诊断结果，不是成功证据。日志可以作为附件，但验收记录还应给出人可读的结论，
不能只贴一段无法定位环境和退出码的输出。

## 11. 文档同步矩阵

实现变更时按下表检查同步范围：

| 变更类型 | 必须检查或更新 |
| --- | --- |
| 公开 API、接口或错误语义 | 设计、头文件注释、示例、测试、兼容性说明 |
| Runtime 状态或转换 | Runtime 设计、状态图、事件 schema、恢复和竞态测试 |
| 并发、取消、定时或 shutdown | 设计、Executor 路由、生命周期测试；能力不足时更新反馈台账 |
| Action 或 Controller | Action 分层、校验规则、安全边界、轨迹/时序测试 |
| Observation、视觉或模型能力 | 数据契约、成本/降级策略、Provider 测试、隐私说明 |
| Context、Memory 或 Replay | 上下文预算、存储 schema、脱敏/保留策略、恢复测试 |
| 产品或技术默认值 | 决策记录、总计划、配置、测试和迁移说明 |
| 安全或权限边界 | 威胁模型、决策、负向测试和事件脱敏规则 |
| 依赖版本或构建组合 | 锁定信息、兼容性矩阵、许可证/SBOM 和回归记录 |
| 性能或实时性声明 | benchmark 方法、结果、目标平台限制和计划门禁 |
| 里程碑范围或状态 | 总计划索引、里程碑文档、依赖方和验证记录 |

同步更新应与实现处于同一变更中。确实需要分阶段完成时，相关工作项保持未完成，并记录后续
编号和负责人，不能以“以后补文档”关闭当前范围。

## 12. Executor 专项流程

所有任务和生命周期继续受根 `AGENTS.md` 约束。设计和计划必须明确每类工作由 Executor 的
哪种能力承载、任务句柄由谁持有、如何取消以及关闭顺序。

当 Executor 公开能力不足时，不得在普通风险列表中一句带过，也不得以裸线程或私有线程池
绕行。必须按 `docs/executor_feedback/ledger.md` 的格式登记 `EXE-YYYYMMDD-NNN`，在相关
设计、计划、代码或测试中引用，并给出临时兼容边界、差异、风险、移除条件和验收标准。

## 13. 兼容性、供应链和基准规则

- 兼容性文档区分“查阅上游资料”“源码或配置确认”“编译通过”和“运行互操作通过”。
- 平台矩阵的空白项代表未知，不代表不支持；未经验证不能改写为支持。
- 依赖升级必须记录旧版本、新版本、来源或 commit、许可证变化、受影响能力和回归结果。
- 性能报告必须保留硬件、系统负载、编译配置、数据集、预热、样本量、统计口径和原始结果
  位置；只报告最佳值不构成有效基准。
- LLM/VLM 或 ONNX 模型结果必须记录模型标识、版本或摘要、输入数据集、评估指标和推理配置，
  同时遵守数据许可、隐私和凭据脱敏要求。

## 14. 评审与变更控制

评审重点按以下顺序进行：

1. 是否符合产品目标、范围和既有决策。
2. 分层、所有权、平台边界和 Executor 生命周期是否正确。
3. 失败、取消、超时、Human Takeover、背压和 shutdown 是否闭合。
4. 安全、隐私、兼容性和迁移风险是否明确。
5. 测试与验证证据是否足以支撑声明。
6. 文档、计划和状态是否同步。

发现实现与文档不一致时，不能默认以任一方覆盖另一方。先判断是实现缺陷还是已批准的设计
变化：前者修复实现，后者按决策流程同步所有受影响文档。

## 15. 归档与替代

已完成的里程碑和历史决策保留在原路径，以保证链接和编号稳定。文档不再适用时标记
`Superseded` 或 `Cancelled`，在开头写明替代文档、日期和原因。仅在文件从未形成有效引用、
内容完全错误且版本历史足以追溯时才考虑删除。

验证产物过大或包含敏感数据时，不直接提交仓库；文档记录受控存储位置、摘要、保留期限和
复现方法。任何公开日志和截图在提交前必须脱敏。

## 16. Markdown 与链接风格

- 文件名使用小写英文和连字符，稳定编号可保留大写，如 `DEC-001-task-state.md`。
- 标题简洁且层级连续；每个文件只有一个一级标题。
- 使用相对链接连接仓库内文档，链接文字描述内容，不使用“点这里”。
- 表格用于稳定映射和矩阵，长篇论述使用段落或列表，避免把整份文档写成超宽表格。
- 命令、路径、类型、状态和 ID 使用反引号；命令块注明语言 `bash`。
- 日期统一为 `YYYY-MM-DD`，状态和版本在文档开头可见。
- 首次使用缩写时解释含义，Mira 公共术语与设计文档保持一致。
- 修改文档后至少检查相对链接、标题结构、代码围栏和被引用文件是否存在。

## 17. 最小变更记录模板

非里程碑性质但需要留存的实施记录可使用：

```md
## YYYY-MM-DD：M1-03 简短结论

- 范围：本次实际改变的行为。
- 依据：关联设计和 `DEC-NNN`。
- 验证：平台、配置、准确命令及结果。
- 限制：未执行项、原因、负责人和补跑条件。
- 同步：已更新的计划、设计、测试及兼容性文档。
```

该记录可以放在对应里程碑的“验证记录”中。不要为每个小提交创建孤立报告；记录粒度应足以
支持里程碑验收、问题定位和结论复现。
